# Evaluation guide

Every number in the README links to a report in [`reports/`](../reports/), and the README's
scoreboard block is regenerated by `make eval` ([ADR-0005](adr/0005-eval-protocol.md)). This page says what
each report measures, which data it runs on and the exact command that regenerates it.

## Ground rules

- `evals/splits.json` fixes, once, which documents belong to each split. A leakage test
  (`tests/unit/test_splits.py`) fails if the same document (by sha256) lands in two splits.
- Thresholds are chosen on `cal` and checkpoints on `dev`; `test` is only measured.
- Lowering a gate, skipping a test or special-casing an eval answer is not allowed; changing a
  gate needs an ADR with evidence.
- Extractor A, Extractor B and any challenger are scored by the same scorers (`evals/scorers/`)
  on the same documents.

## Datasets

| Dataset | Used for | How to get it |
|---|---|---|
| UAE factory invoices (5,000; 3,500 / 750 / 750, 25% Arabic-first, 30% scans) | Extraction, parsing, e-invoice, fraud, training B | `make factory` (deterministic per seed) |
| FATURA (10,000 invoice images) | Part of B's training mix; the FATURA test split was not evaluated in v1.0 | `uv run python -m evals.datasets fetch --set fatura` |
| ExtractBench (252 short documents) | Value and grounding F1 against a published baseline | `uv run python -m evals.datasets fetch --set extractbench` |
| DocILE | KILE / LIR field metrics | `... fetch --set docile` with an access token (not run in v1.0) |
| PINT AE 1.0.4 samples and schematron | E-invoice validity | `uv run python -m evals.pint_ae.fetch` |
| Attack suite (312 cases, 12 categories) | Injection and payment-redirect resistance | `uv run python -m attacks.generate` |

Downloads land in `data/` (gitignored) and are recorded with hashes in `data/manifest.json`.

Long GPU jobs are resumable: `evals.extraction_a` appends one row per document to a JSONL file
and skips documents already scored, so an interrupted run continues where it stopped. Rows
written under an older row schema are re-run (schema 4: before it, scanned documents were fed as
their born-digital PDF).

### Scanned documents

30% of the UAE factory invoices carry an Augraphy scan variant (`has_scan` in the truth file,
pages in `<sha>.pageN.scan.png`). The extraction eval (`evals.extraction_a`, both extractors)
and the e2e run (`scripts/e2e_pipeline.py`) feed such a document the way the runtime receives a
scan: its scan pages assembled into an image-only PDF (`evals.scan_input`, A4 at 96 dpi, no
text layer), so the parser sends every page to the OCR service and the model sees the scan
render. Born-digital documents are fed as their PDF. Label boxes, the scan raster and the
service's boxes share one page-fraction frame, so the same scorer and box IoU apply to both.
Every row records `input_kind` (`digital` or `scan`), and `reports/extraction_a_adr0012.md` splits every
metric by input kind, by English-first vs Arabic-first layout, and by both. The e2e run writes
the scanned uploads under `data/e2e_scans/`.

## The quality gates

Measured results and their targets are in the README under [Results](../README.md#results),
and the generated scoreboard holds every target row with its status. The promotion gates for a
new Extractor B are in [ADR-0015](adr/0015-promotion-gates.md) and ADR-0009 §1.8.

## Verify targets

`make verify-m0` to `make verify-m12` group the checks by build stage (for example `make
verify-m2` regenerates the factory, then re-runs the label self-check and the gold XML check).
`verify-m3`, `verify-m6` and `verify-m9` to `verify-m12` are stubs that print "not implemented
yet" and exit 1, so `make verify-all` fails. CI runs lint, types, unit tests and the header check
on every pull request.
